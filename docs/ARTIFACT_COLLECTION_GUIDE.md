# Publication Artifact Collection Guide

This document is the **master checklist for converting the PoI architecture into publication-grade empirical artifacts**.

The goal is not to collect “many charts.” The goal is to collect **one defensible evidence object for every central claim**.

## 1. Artifact philosophy

For every claim in the paper, collect four layers:

1. **Raw artifact** — trace files, audit outputs, gas reports, challenge logs, evaluator outputs.
2. **Machine-readable aggregate** — CSV/JSON/Parquet generated by code.
3. **Paper artifact** — table, chart, algorithm, or architecture figure.
4. **Provenance** — config hash, git commit, dataset manifest, hardware/software environment.

Never manually transcribe experimental numbers into the manuscript.

---

## 2. Paper-to-artifact map

| Paper concept / section | What to collect | Publication artifact | Minimum evidence |
|---|---|---|---|
| Problem definition | Threats, requirements | Requirement matrix table | 1 table |
| SPAI single-pass idea | Runtime and trace timings | Cost figure + cost table | 3 baselines |
| Base commitment | Actual commitment records | Algorithm + sample commitment object | 20+ example receipts |
| Post-commit audit seed | Seed derivation logs | Algorithm + timing diagram | 1 reproducible seed protocol |
| Open-weight execution assurance | Trace/tensor audit outcomes | Detection curve + audit coverage table | ≥4 sampling rates |
| Optimistic dispute | Challenge transcripts | Sequence diagram + dispute metrics | ≥100 injected faults |
| IEC | Claim/evidence structures | IEC schema table + coverage chart | ≥500 grounded items |
| Semantic assurance | Correct/incorrect/ambiguous decisions | FAR/FRR/ABSTAIN figure + confusion matrix | ≥500 items |
| DA | Shard creation, withholding, sampling | Theoretical-vs-empirical curve | ≥5 withholding rates |
| Economics | Credit/bond/task allocation | Attack-cost curve + concentration plot | ≥1,000 simulation seeds |
| Sybil neutrality | Identity split scenarios | Sybil advantage plot | 1–64 identities |
| Consensus | Receipt → next epoch weight | Weight distribution figure + committee table | ≥100 simulated epochs |
| EVM | Contract calls | Gas/state table | 5+ call types |
| Frontier scaling claim | Model size vs trace/audit cost | Scaling curve | ≥2 model sizes |
| Reproducibility | Environment/commands | Reproducibility manifest | one-click replay |

## 3. Required tables for the paper

### Table T1 — System requirements and protocol response

Columns:

`Requirement | Threat if absent | Protocol mechanism | Test ID | Evidence`

Use this near the introduction/method section.

### Table T2 — Protocol object/schema table

Columns:

`Object | Commitment/root | Contents | Mutable? | On-chain/off-chain | Verified by`

Rows should include:

`C_P, C_T, C_M, C_R, R_X, R_E, C_A, AuditRoot, Nullifier, R_I, Q_i, W_i`

### Table T3 — Assurance tiers

Columns:

`Tier | Execution evidence | Trust assumptions | Audit cost | Consensus eligibility`

Do not mix a TEE-only receipt with a cryptographic receipt without making the assurance class explicit.

### Table T4 — Dataset composition

Columns:

`Dataset | Task family | N | Positive | Negative | Ambiguous | Source | Generator version`

### Table T5 — Experiment configuration

Columns:

`Experiment | Model | Dataset | Audit rate | Freivalds rounds | DA samples | Threshold | Seed | Hardware`

### Table T6 — Single-pass cost

Columns:

`Model | Baseline | Inference ms | Trace overhead ms | Audit ms | Dispute amortization | Total expected ms | GPU energy/cost`

Baselines:

`Single-run`, `Two-run`, `MPP-SPAI`.

### Table T7 — Execution audit security

Columns:

`Attack type | Audit setting | Trials | Detected | Missed | Detection rate | 95% CI`

### Table T8 — Semantic verification

Columns:

`Task class | N | TP | FP | FN | TN | FAR | FRR | ABSTAIN | Expert agreement`

### Table T9 — Data availability

Columns:

`Withheld fraction f | DA samples k | Theoretical P_miss | Empirical P_miss | Reconstruction rate`

### Table T10 — Watcher/dispute economics

Columns:

`Fraud value | Audit cost | Challenge bond | Reward | Watchers | P(challenge) | P(maturity) | Watcher EV`

### Table T11 — Sybil economics

Columns:

`Identities | Capacity model | Expected credit | Baseline credit | Sybil advantage | 95% CI`

### Table T12 — EVM boundedness

Columns:

`Contract call | Gas median | Gas p95 | Storage delta | Calldata bytes | Repeated-task frequency`

### Table T13 — Consensus safety simulation

Columns:

`Scenario | Epochs | Adversarial strategy | Max active weight | BFT threshold crossed? | Probability | Cost`

### Table T14 — Artifact/reproducibility matrix

Columns:

`Result ID | Script | Input config | Raw artifact | Generated figure/table | Commit hash`

## 4. Required figures / charts

### Figure F1 — End-to-end protocol architecture

Keep as a systems architecture diagram. It should show:

`Task -> Execute once -> Trace/IEC -> Commit -> Post-commit randomness -> Audit -> Dispute/DA -> Matured receipt -> PoI weight`.

Use arrows to distinguish:
- synchronous request path
- asynchronous audit path
- consensus path

### Figure F2 — SPAI sequence diagram

Actors:

`Requester | Worker | Settlement chain | Auditor | Watcher | DA layer | Consensus client`

Show:

1. Task issuance.
2. Single model execution.
3. Response/trace/IEC commit.
4. Commitment finality.
5. Audit seed reveal.
6. Audit opening.
7. Optional dispute.
8. Receipt maturity.
9. Next-epoch weight.

### Figure F3 — Execution-audit architecture

Show:

`model -> trace sidecar -> trace Merkle root -> sampled tensors -> Freivalds check -> exact cheap-op checker -> dispute micro-step`.

### Figure F4 — Semantic verification architecture

Show:

`response -> IEC -> task obligations -> objective checks / evidence checks / semantic verifier / metamorphic checks -> LCB -> ACCEPT / ABSTAIN / REJECT`.

### Figure F5 — Single-pass cost comparison

X-axis: model size or token count.

Y-axis: normalized total verification cost.

Curves:

`two-run baseline`, `MPP-SPAI`, optionally `full-zk reference` if measured.

Do not show theoretical curves as empirical. Use dashed lines or separate panel only if labeled “model”.

### Figure F6 — Audit soundness curve

X-axis: audit sampling rate.

Y-axis: attack escape probability / detection probability.

Show theoretical randomized-check bound and empirical result together.

### Figure F7 — Semantic verification quality

Preferred:
- FAR/FRR/ABSTAIN stacked bar by task class, or
- ROC/PR only if the verifier outputs continuous scores.

Also include a calibration plot if a score threshold is used.

### Figure F8 — DA withholding

X-axis: withheld fraction.

Y-axis: probability of undetected withholding.

Overlay theoretical `(1-f)^k` and empirical points with confidence intervals.

### Figure F9 — Sybil advantage

X-axis: number of identities controlled by the same operator.

Y-axis: normalized expected protocol credit.

Ideal outcome is approximately flat.

### Figure F10 — Economic security

X-axis: adversarial active-weight target.

Y-axis: minimum estimated acquisition cost.

Compare:

`honest market`, `subsidized compute`, `external resale value`, `collateral-bounded`.

### Figure F11 — Consensus dynamics

Show one epoch timeline:

`work epoch e -> audit -> challenge window -> mature -> Q^(e+1) -> W^(e+1) -> committee`.

### Figure F12 — EVM gas/state scaling

X-axis: receipts per batch.

Y-axis: gas or storage growth.

Show median and p95.

## 5. Required algorithm disclosures

The paper should publish **at least four algorithms** as pseudocode.

### Algorithm A1 — Single-Pass Auditable Intelligence (SPAI)

Purpose: define the atomic intelligence event.

Required steps:

`ExecuteOnce -> BuildTrace/IEC -> Commit -> Finalize -> Seed -> Audit -> Verify -> Dispute -> MatureReceipt`.

### Algorithm A2 — Post-Commit Audit Compiler

Purpose: map public policy + unpredictable seed to concrete audit obligations.

Inputs:

`C_P, C_T, C_R, epoch_beacon, task_family`.

Outputs:

`S_X, S_S`.

Important invariant:

`C_R finality < audit-seed revelation`.

### Algorithm A3 — VerifySPAIEvent / VerifyIntelligence

Purpose: canonical validity predicate.

It must explicitly return:

`ACCEPT | ABSTAIN | REJECT`.

### Algorithm A4 — PoI Credit and Next-Epoch Weight

Purpose: map matured receipts to consensus authority.

Core equations:

`sum_i c_ij <= D_j`

`Q_i^(e+1) = sum_j c_ij`

`W_i^(e+1) = min(Q_i^(e+1), B_i/beta, ConcentrationCap_i)`

`p_i = W_i / sum_k W_k`.

### Optional Algorithm A5 — Optimistic Dispute Bisection

Publish only if the prototype actually implements it. Otherwise keep it as architecture pseudocode and label the full implementation as future work.

## 6. Algorithm presentation format

For every algorithm in the paper include:

1. Inputs.
2. Public state.
3. Private witness/state.
4. Preconditions.
5. Numbered steps.
6. Output.
7. Failure/ABSTAIN states.
8. Security invariant.
9. Complexity note.
10. Which experiment validates it.

Example security invariant for A2:

`The worker cannot know concrete S_X/S_S before C_R becomes irreversible.`

Example complexity statement:

`O(k) sampled audit openings + O(log n) Merkle verification per opened trace object`, subject to the concrete trace layout.

Do not state asymptotic complexity unless it matches the actual implementation.

## 8. Raw data that must be preserved

Never publish only averages.

Keep:

- per-task model/version ID
- task ID
- input hash
- response hash
- trace root
- evidence root
- audit seed
- sampled audit IDs
- audit outcome
- semantic scores per verifier
- LCB score
- ABSTAIN reason
- DA sampling outcome
- dispute state
- receipt state
- credit
- active weight
- runtime and hardware ID
- wall-clock timings
- GPU/CPU utilization where available
- gas used
- random seeds
- config hash
- software commit hash

Privacy rule: store only hashes or redacted artifacts where user prompts/evidence are sensitive.

## 9. What belongs in the paper vs repository

### Paper

Keep only the minimal information necessary to understand and evaluate:

- definitions
- equations
- protocol algorithms
- architecture figures
- experimental methodology
- aggregated results
- confidence intervals
- ablations
- limitations

### Repository

Put detailed artifacts here:

- raw JSONL/CSV/Parquet
- full receipts
- trace samples
- audit transcripts
- failed/disputed cases
- Solidity contracts
- deployment scripts
- model adapter
- all experiment scripts
- environment lock
- result-generation scripts
- exact configs
- seeds
- Docker/uv environment

Use stable IDs.

Examples:

`E1_cost_qwen15b_seed0042.csv`

`E2_tamper_freivalds_r08_sample05.jsonl`

`E3_grounded_semantic_v1.parquet`

`F5_single_pass_cost.pdf`

`T7_execution_audit_security.csv`

`R_00001234.json`

`commitment_task_00001234.json`

The same ID must appear in the paper's artifact/reproducibility appendix.

## 11. What counts as a real publication artifact

A chart is publication-ready only if:

- it is generated from raw machine-readable data;
- the generation script is committed;
- axes and units are explicit;
- confidence intervals are included when appropriate;
- sample size is visible;
- model/version/config are stated;
- no manually typed data are used;
- the result can be reproduced from a clean environment.

A diagram is publication-ready only if:

- every arrow corresponds to a protocol message/state transition;
- no unimplemented component is shown as if it were implemented;
- trust boundaries are visible;
- synchronous vs asynchronous paths are distinguishable;
- cryptographic proof vs attestation vs heuristic semantic verification are visually distinct.

---

## 12. Publication evidence priorities

If engineering time is limited, prioritize in this order:

1. E1 single-pass cost.
2. E2 execution tamper detection.
3. E3 semantic FAR/FRR/ABSTAIN.
4. E6 Sybil/economic safety.
5. E7 EVM boundedness.
6. E4 DA.
7. E5 watcher/dispute economics.
8. E8 full consensus simulation.

The first five create the strongest evidence for the paper's central claims.
